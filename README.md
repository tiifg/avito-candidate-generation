# avito-candidate-generation

Решение задачи candidate generation: по поисковому запросу отобрать из корпуса
до 50 объявлений-кандидатов, которые дальше пойдут на этап ранжирования.
Целевая метрика - Recall@50.

## Результат

- **Recall@50 на платформе: 0.522**
- Baseline (TF-IDF + popularity): 0.318
- Промежуточная версия (TF-IDF + collaborative): 0.483

## Подход

Гибридный лексический retrieval с обучаемыми приорами. Пять источников
сигнала, чьи скоры нормируются на максимум внутри запроса и складываются
с весами W:

| Источник | Идея | Вес |
|---|---|---|
| BM25 | Okapi BM25 по слову и биграммам, текст объявления расширен кликовыми запросами | 1.00 |
| char TF-IDF | `char_wb` 3-4 граммы, устойчивость к опечаткам и морфологии | 0.55 |
| Collaborative kNN | Похожие train-запросы -> их выбранные объявления | 0.85 |
| Приор микрокатегории | Rocchio-центроид, top-8 микрокатегорий | 0.35 |
| Приор категории | Rocchio-центроид, top-3 категорий | 0.15 |
| Приор локации | P(item_location \| search_location) из train | 0.20 |
| Популярность | log1p числа выборов в train | 0.06 |
| Рейтинг | item_rating / 5 | 0.03 |


**BM25 вместо чистого TF-IDF.** Okapi BM25 с нормировкой по длине документа
и насыщением TF лучше работает на коротких запросах, где важна точность,
а не полнота. Реализация векторизована: IDF и нормировка по длине зашиты
в матрицу документов, скор запроса - одно sparse-умножение.

**Кликовое расширение текста объявления.** В `train.parquet` есть пары
«запрос -> выбранное объявление». Для каждого объявления корпуса собираем
до `CLICKS_PER_ITEM = 25` уникальных запросов, по которым его выбирали,
и подмешиваем их в `word_text` трижды (вес как у заголовка) и в `char_text`
один раз. Это расширяет текстовое представление объявления реальными
формулировками пользователей.

**Char n-grams (3-4).** Русский язык не прост. `телевизор`,
`телевизора`, `телевизоров` - три разных токена для word-BM25. Char n-grams
устойчивы к этому, а также к опечаткам и слитному написанию. В `char_text`
идет только заголовок + параметры + кликовые запросы (без описания), обрезка
до 300 символов - так словарь остается компактным.

**Collaborative kNN.** Строим TF-IDF-пространство уникальных train-запросов
(`UQ`). Для каждого benchmark-запроса находим `top-50` ближайших
(`COLLAB_TOPK = 50`), оставляем только их через `topk_mask` и умножаем
на разреженную матрицу `CL` (`unique_train_query × item`). Получаем
«голосование» похожих запросов: если группа похожих train-запросов
стабильно выбирает объявления из одной группы - они получают высокий скор.

**Rocchio-центроиды для категорий.** Для каждой микрокатегории (и категории)
строим центроид - L2-нормированную сумму tf-idf векторов запросов, которые
привели к объявлениям этой категории. При инференсе косинус запроса
с центроидами даёт «уверенность» в категории. Оставляем top-8 микрокатегорий
и top-3 категорий через `topk_mask`, остальное обнуляем - иначе слабые
категории создают шум.

**Приор локации.** Для каждой `search_location_id` считаем распределение
`item_location_id` по train. Нормируем на максимум и складываем с весом
`W["loc"]`. Работает как мягкий тай-брейк: если запрос из Москвы, слегка
поднимаем московские объявления.

**Нормировка на максимум внутри запроса.** `rowmax_norm` делит каждую строку
скоров на ее максимум. Разные источники имеют разный масштаб (BM25 - десятки,
char-TF-IDF - десятые), без нормировки веса `W` не имели бы смысла.

## Данные и признаки

Использованы три файла: `train.parquet`, `benchmark_queries.parquet`,
`benchmark_items.parquet`.

### Из запроса

- `search_query` - основной текстовый сигнал, повторяется трижды в `_q`.
- `search_infm_params_text` - фильтры поиска, добавляются в `_q`.
- `search_category` - не используется напрямую, но входит в ключ валидации.
- `search_location_id` - для приора локации.
- `search_is_delivery_search` - входит в ключ валидации.

### Из объявления

- `item_title_raw` - заголовок, трижды в `word_text`, один раз в `char_text`.
- `item_infm_params_text` - параметры услуги, дважды в `word_text`.
- `item_description_raw` - описание, обрезается до 1200 символов.
- `item_category_id`, `item_microcat_id` - целевые классы Rocchio.
- `item_location_id` - для приора локации.
- `item_rating` - слабый буст качества.
- `item_id` - ключ для кликового расширения.

### Из train

- `item_id` - популярность, кликовое расширение.
- `search_query` - для кликового расширения (нормализованный вид).
- Пары `(search_*, item_*)` - Rocchio-центроиды, приор локации, collaborative.

## Алгоритмы и библиотеки

- **BM25 (Okapi)** - собственная реализация на `scipy.sparse`.
  Формула: `idf = log(1 + (N - df + 0.5) / (df + 0.5))`,
  `tf_norm = tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl))`,
  `k1=1.2`, `b=0.6`.
- **TF-IDF** - `sklearn.feature_extraction.text.TfidfVectorizer`
  (`char_wb` 3–4 для объявлений, `word` 1-2 для пространства запросов).
- **CountVectorizer** - для BM25-индекса.
- **Rocchio-центроиды** - `scipy.sparse` + `sklearn.preprocessing.normalize`.
- **Русский стемминг** - `nltk.stem.snowball.SnowballStemmer("russian")`.
- Все вычисления локальные, без внешних API.

## Проверка качества

Локальная валидация встроена в исходную версию (`make_validation`).
Она:

1. Группирует `train.parquet` по полному набору `search_*` признаков -
   получается псевдо-`query_id`. Уникальных групп ~N.
2. Сэмплирует 2000 групп как «запросы бенчмарка».
3. Полностью исключает строки этих групп из обучающей части - иначе
   кликовое расширение и collaborative дали бы утечку.
4. Считает Recall@50 на отложенных группах.
5. 

Дополнительно проверяется формат `answer.csv`:

- число строк = число запросов бенчмарка;
- `query_id` уникальны;
- не больше 50 `item_id` в строке;
- без повторов внутри строки;
- все `item_id` существуют в `benchmark_items.parquet` и имеют формат
  `[0-9a-f]{16}`.

## Найденные ошибки и что с ними сделано

**1. Утечка в LightGBM-ранкере.** Промежуточная версия с ранкером дала
Recall@50 = 0.246 - хуже baseline. Причина: в фичу `collab_score` попадало
сходство train-запроса с самим собой (=1.0), positives получали аномально
высокий скор, модель училась на сигнале, которого нет на инференсе.
Решение: отказалась от ранкера в пользу явного гибридного скоринга
с подобранными весами `W`.

**2. Потеря ведущих нулей в ID.** При чтении parquet pandas может парсить
`item_id` и `query_id` как числа. Решение: `astype(str)` сразу после
загрузки, все проверки формата через `re.fullmatch(r"[0-9a-f]{16}", ...)`.

**3. Долгая нормализация текстов.** Стемминг 190k объявлений занимает
несколько минут. Решение: кэш `item_text_cache.pkl` - при повторных
запусках нормализация пропускается. Файл инвалидируется вручную при
смене логики нормализации.

**4. Рассинхрон масштабов скоров.** BM25 даёт скоры порядка 10–30,
char-TF-IDF - порядка 0.1–0.5. Без нормировки бусты и приоры «тонули».
Решение: `rowmax_norm` - деление каждой строки скоров на ее максимум
перед умножением на вес.

**5. Шум от Rocchio-классификатора.** Классификатор дает ненулевой скор
всем категориям. Слабые категории создают шум. Решение: `topk_mask` —
оставляем только top-8 микрокатегорий и top-3 категории, остальное
обнуляем.

**6. Медленный инференс на 2452 запросах.** Полная матрица
`(2452, 189212)` около 3.7 ГБ. Решение: батчинг по `BATCH = 64`.

**7. Разные масштабы collab-скоров на train и inference.** На train
ближайшим соседом запроса почти всегда оказывается он сам. Это нормально для
инференса, но при валидации мы исключаем строки отложенных групп из
обучающей части - поэтому утечки нет.
